# 简历可用文本与面试材料：AI 经营分析与 7 天验证助手

本文件提供不含私人联系方式的**简历可用项目文本**。个人简历 PDF 另行维护；使用前请核对个人职责，只保留自己真实参与、能够说明并提供证据的内容。

项目代码：[GitHub 仓库](https://github.com/Heart727/business-validation-lab)。公开体验：[经营验证工作台](https://business-validation-lab.vercel.app)。使用说明：[新手指南](user-guide.md)。项目背景与已有证据：[案例说明](case-study.md)。

项目是个人求职作品，使用虚构资料和专用飞书 DEMO 表。2026-10-12，10 份不同资料通过本地 FastAPI API 调用真实 Dify/DeepSeek 和飞书，完整验收结果见 [记录](live-acceptance.md)。模拟测试、真实接口验收和真实经营成果分别表述，不将演示称为雇主任职或商业客户交付。

## 一、可复制到简历的项目条目

### 一段式版本

**AI 经营分析与 7 天验证助手｜个人项目｜产品需求与集成实践，Codex/AI 辅助开发。** 围绕小商家“如何把经营问题变成可验证的小实验”设计虚构演示流程：从十份模板填入受限表单，经虚构资料确认后生成经营摘要、证据、推断、缺失信息、风险和七天行动，资料快照与结果保存至飞书多维表格；通过记录专属令牌支持同一浏览器恢复最近报告，逐天记录状态、指标与结论，保存日志不再次调用 AI。技术栈为 FastAPI、Pydantic、原生 HTML/CSS/JavaScript、Dify、DeepSeek、飞书 Bitable 和 Vercel；项目代码由 Codex/AI 辅助生成与修改，我的职责表述聚焦实际参与的需求梳理、集成配置和验收理解。

### 要点版

以下职责只有在本人实际参与后才适合复制进简历；如由协作者代为完成，应改成“参与”或删去对应表述。

- 梳理虚构演示的产品要求，明确九个经营字段、资料边界、AI 报告结构及七天执行记录流程，避免把 AI 推断写成已验证的经营事实。
- 参与 Dify/DeepSeek、飞书演示表与 Vercel 的集成配置和核对，围绕“提交资料是否传入工作流、结果是否保存、失败是否能恢复”定义验收检查点。
- 在 Codex/AI 辅助编码下完成项目交付，能够说明同一 UUID 与同一输入重试、资料冲突拒绝、记录专属访问令牌、逐天独立保存等设计与限制；以可核对的验收证据说明实际完成范围。
- 项目通过 10 份不同虚构资料的真实集成验收，核对报告结构、资料快照、原请求重试和日志读回；另验证 422 输入拒绝、409 内容冲突与 403 伪造令牌拒绝，保留输入/输出证据。

如果尚不能解释上述机制，可以先使用保守版本：

> AI 经营分析与 7 天验证助手，个人学习与求职展示项目。借助 Codex/AI 辅助开发，学习将受限的虚构经营资料接入 Dify/DeepSeek 工作流，并通过飞书多维表格保存分析与七天执行日志；参与需求讨论、集成配置核对和验收材料整理。项目仅用于虚构演示，不包含真实客户或经营收益证明。

不要写“独立手写全部前后端”“为某公司上线”“帮助商家营收增长”或“已证明模型提升经营效果”。没有对应证据时，也不要写全部真实案例已通过验收。

## 二、个人职责与 AI 辅助的诚实口径

可用下面的分工解释项目。它是职责核对框架，不能替代本人参与记录：

| 范围 | 候选人应如实说明的参与 | Codex/AI 的辅助范围 |
| --- | --- | --- |
| 产品需求 | 目标用户、问题定义、虚构数据限制、字段与流程取舍；说清哪些要求由本人提出或确认 | 整理需求、给出方案与文档草稿 |
| 集成配置 | 哪些平台账号、工作流发布、演示表权限或部署配置由本人操作，哪些由协作者执行 | 配置步骤、接口对接代码与排错建议；不能把 AI 建议等同于本人实际配置 |
| 编码实现 | 说明自己读懂、核对或修改了哪些部分；不把生成代码说成逐行手写 | 生成和修改前后端代码、服务接口、校验及相关检查内容 |
| 验收理解 | 解释成功条件、核对资料快照与日志、区分假服务验证和真实集成；亲自操作过的范围单独说清 | 协助生成检查步骤、运行记录与材料；结果仍需用实际输出证明 |

“AI 辅助开发”说明的是项目建设过程；“Dify/DeepSeek 生成经营分析”说明的是产品运行时能力。两者应分别介绍。

如果被问“代码是你写的吗”，可以据实回答：

> 这个项目使用了 Codex/AI 辅助编码，不能说所有代码都是我逐行手写的。我会具体说明自己参与的需求决策、平台配置和验收核对，也会说明代码生成与修改中 AI 的作用。对于我讲到的设计，我能结合代码和运行记录解释；尚未掌握或尚未验证的部分，我会直接标明。

## 三、面试时先讲问题，再讲闭环

### 项目解决的具体问题

小商家可能有“要不要做活动、投放或调整服务”的想法，但没有统一的基线、观察指标和结束条件。项目的目标是把模糊问题变成一份有依据边界和判断条件的七天计划，并留出执行记录入口。

当前范围是虚构演示，不是自动经营决策系统。AI 可以组织资料、提出假设与行动，但无法证明资料真实，也无法仅凭生成文本证明商业效果。

### 两条流程怎么连起来

**分析流程**：浏览器选择模板并修改受限经营字段 → FastAPI 校验字段、虚构确认和请求 UUID → 飞书记录资料快照和处理状态 → Dify Workflow 调用 DeepSeek → Pydantic 校验报告结构 → 更新同一条飞书记录 → 浏览器显示报告并保存记录访问令牌。

**执行流程**：浏览器提交该记录的请求 ID、访问令牌及某一天的状态、指标、结论 → 服务端核对记录访问权限 → 更新飞书对应日期的执行字段 → 返回已保存内容。该流程不经过 AI；恢复报告也读取已有记录。

### 值得说明的设计决策

- **输入有边界**：十份模板降低填写门槛，九个字段限制长度，要求虚构确认并做部分敏感内容检查。检查是辅助，不能保证识别全部隐私或阻止所有不合规输入。
- **同一请求不混入新资料**：同一 UUID 的重试必须保持输入一致；更改内容返回 `request_content_conflict`，要重新分析就生成新 UUID。这有助于避免报告和资料快照对不上。
- **输出先校验再完成**：报告要包含摘要、证据、推断、缺失信息、风险及七个不同日期的行动。结构合格说明可用来展示，不说明推断已经正确。
- **访问按记录授权**：编辑请求使用独立私有请求令牌；成功后获得报告访问令牌，浏览器保存最近一条。展示 UUID 不授予读写权限；恢复码持有人能访问对应记录，可手动转移到新设备。项目未实现账号体系或账号找回。
- **执行记录与 AI 分开**：每天单独保存指标与结论，修改一天不覆盖其他天，也不为记录日志重复调用模型。原分析不会因日志变化自动更新。
- **演示资源受限**：分析、重试、恢复、保存合计每 IP 每 10 分钟最多 5 次；仍依赖模型额度、工作流、飞书及部署平台可用性。不能承诺服务一直可用或所有重试都不消耗模型额度。

## 四、90 秒面试演示脚本

已补充 [90 秒操作视频](https://business-validation-lab.vercel.app/static/demo/index.html)，配有中文字幕和中文合成讲解，使用虚构咖啡店资料。视频实际读取此前已生成的真实报告、保存日志并刷新恢复；完整时间线和证据见 [录制说明](demo-video.md)。下表是现场演示的排练脚本，使用虚构早餐配送资料；AI 耗时不固定，展示备用报告时明确说明它是已有记录。

| 时间 | 屏幕操作 | 建议口播 |
| --- | --- | --- |
| 0–15 秒 | 打开公开网页，选择早餐配送模板 | “这是我的个人求职项目，用 Codex/AI 辅助开发。我参与需求和集成核对，演示只使用虚构资料。它把经营问题整理成可执行、可记录的七天小实验。” |
| 15–35 秒 | 指出基线和目标字段，确认虚构资料并提交 | “这里把基线改成每天四十单、提前预订八单，目标是观察预订占比能否达到百分之三十。输入和目标分开填写，确认虚构后提交，资料快照与分析保存到飞书演示表。” |
| 35–55 秒 | 指出摘要、证据、推断、缺失信息和风险 | “报告区分资料中的证据、模型推断和仍缺的信息。推断不是事实，目标也不是成果。下面七天动作分别写明要做什么、观察什么，以及判断条件。” |
| 55–75 秒 | 保存第 1 天虚构执行记录，再刷新读取 | “我给第一天填写虚构指标和结论，保存只更新当天记录，不再调用 AI。成功后的专属令牌保存在当前浏览器，刷新可读取最近报告和已保存日志。” |
| 75–90 秒 | 展开已保存资料快照，指出限制 | “十份不同虚构资料已经完成真实接口验收，输入输出都留了证据。执行日志只是演示，不能证明经营收益；没有账号找回，四类接口共享每 IP 十分钟五次的额度。” |

如果提交仍在等待，用一句“这次正在请求外部服务，接下来用之前保存的报告解释结构”切换到备用记录；不要把备用记录说成本次新生成。若现场报错，展示安全错误提示并说明保持原输入和 UUID 重试。需要演示飞书时由所有者登录并提前准备脱敏视图，面试官不必拥有表格权限。

## 五、常见追问与回答要点

### 为什么不是直接让模型回答一个经营问题？

重点在于把输入、输出、保存和后续观察串起来。受限资料便于确认分析依据，结构化输出便于读懂和记录，资料快照便于核对，执行日志便于对照计划。AI 文本本身不能替代实验结果。

### 怎么判断这次分析成功？

需要报告结构合格，并且同一条飞书记录保存完成。不能只看模型返回了一段话。进一步应核对提交修改确实传给工作流、资料快照与输入一致、原 UUID 重试返回关联记录，以及执行日志保存后能读回。

### 为什么重试必须保留输入？

UUID 关联本次资料和记录。复用 UUID 但修改目标，可能使旧报告被误当成新资料的分析，所以系统拒绝内容冲突。正常重试复用同一条记录；修改需求则新建分析。幂等处理减少重复记录，不等于保证模型只被调用一次。

### 七天记录的“实际指标”是不是实际经营成果？

这个公开 DEMO 里只能填虚构观察值。指标字段展示的是记录能力，不是证明团队已经做了真实经营实验。一天数据也不足以证明因果关系；真实使用还需要统一口径、样本量、成本和预先约定的继续或停止门槛。

### 没有登录，别人能改我的记录吗？

当前网页产生的编辑请求绑定私有请求令牌，报告读取与执行保存还校验记录访问令牌；仅知道展示 UUID 不能获得授权。令牌持有人可以查看和修改，共用浏览器也可能恢复最近记录。恢复码可手动跨设备使用；没有账号归属验证、账号找回或逐条令牌撤销，服务端密钥轮换会使旧访问令牌失效。兼容旧固定样例接口的请求不签发执行记录令牌。

### 保存记录会重新分析吗？

不会。它只更新对应日期的执行字段，其他日期保留，原 AI 报告也保留。读取或保存仍依赖飞书服务可用；如果保存失败，应重试该天保存，不需要重新生成 AI 计划。

### 做了多少验收？

2026-10-12，十份不同的编辑资料通过本地 API 调用真实 Dify/DeepSeek 和飞书：资料快照、完整七天报告、原请求重试及第 1 天虚构执行记录读回全部通过；三个输入/授权错误边界也实际验证。模拟服务另外覆盖上游超时与读写失败。证据见 [验收记录](live-acceptance.md)。这不是十家真实客户，也不是已经完成十个七天经营实验。

### 下一步会做什么？

如果要用于真实经营，首先重新设计资料授权、隐私与存储规则，再考虑账号归属、历史记录、令牌管理、持久任务和可观测性。这些是后续方向，不应说成当前已完成的能力。商业效果仍需真实执行和合适的评估设计证明。

## 六、展示材料和证据边界

公开演示可以放在简历或面试材料里；[飞书演示表（所有者权限，非公开）](https://qcngavuynwd3.feishu.cn/base/VYR4bKwbra78eXs9sMvcmyLMnsd?table=tblMOuyhUydfHArG&view=vewdYYnCuU)只用于所有者核对记录，不应承诺面试官可以直接访问。

整理一份验收证据时，应保留：运行日期与环境、虚构输入及修改点、请求 ID、报告结构、脱敏飞书资料快照、相同输入重试关联情况，以及至少一条执行记录保存和刷新读回的结果。截图不包含访问令牌、平台凭证、真实客户信息或账号敏感内容。

可证明的成果应分开描述：

| 成果类型 | 合适的证据与措辞 |
| --- | --- |
| 产品与实现范围 | 页面和代码能够展示受限表单、结构化报告、恢复及执行记录；说明 AI 辅助开发方式 |
| 本地流程验证 | 明确标注假服务、模拟输入和验证范围；不算作真实外部调用 |
| 真实集成验收 | 10/10 不同虚构输入完成真实 Dify/飞书流程，留有资料快照、AI 输出、请求/记录 ID 和日志读回证据 |
| 真实业务效果 | 目前没有可用于宣称营收、利润或效率提升的真实经营证据 |

候选人最终应能把“我参与了什么”“系统做了什么”“哪些已经验证”“哪些仍有限制”分别讲清楚。用可核对的个人参与和演示结果支撑项目价值，不补造雇主、客户、商业收入或经营改善。
