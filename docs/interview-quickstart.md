# 面试速记：两分钟讲清项目，再让对方亲自验证

[公开体验](https://business-validation-lab.vercel.app/) · [90 秒视频](https://business-validation-lab.vercel.app/static/demo/index.html) · [一页项目案例 PDF](https://business-validation-lab.vercel.app/static/demo/project-case.pdf) · [代码与验收](https://github.com/Heart727/business-validation-lab)

这份材料用于 AI 应用开发方向的项目介绍。原有 [详细面试问答](resume-project.md) 保留完整设计和职责边界；这里集中准备开场、现场操作和最容易被追问的部分。

## 两分钟开场

按自己的语速排练，下面约两分钟。个人职责只保留自己实际参与、能够解释的内容。

**0–25 秒：问题与使用者。**

> 这个个人求职作品面向小微商家的经营问题。比如一家虚构咖啡店想改善下午客流，只有“做活动”的想法，却没有明确基线和判断条件。这个应用让访客从模板填写经营资料，得到一份七天验证计划，再逐天记录观察指标和结论。

**25–60 秒：系统怎么跑。**

> 浏览器把十个经营字段提交给 FastAPI。服务端检查资料边界，先在飞书保存资料快照，再调用 Dify 工作流，由 DeepSeek 生成分析。Python 校验摘要、证据、推断、缺失信息和七个不同日期的动作，合格后更新同一条记录。报告不是看到一段模型文字就算成功，还要确认保存完成。

**60–90 秒：验收与失败。**

> 项目用十份不同虚构资料接真实 Dify 和飞书，核对报告、输入快照、原请求恢复和日志读回；公开网站也完成过匿名浏览器验收。明显联系方式会被拒绝，同一请求换资料会报冲突，伪造访问令牌不能读取记录。日志保存不调用 AI，刷新会恢复最近报告。

**90–120 秒：个人参与与边界。**

> 这个项目由我使用 Codex 辅助搭建。我负责确认展示需求与使用边界，提供并授权连接平台账号；编码、集成操作、测试与部署由 Codex 辅助完成。我会结合代码说明自己实际参与和掌握的部分。现在交付的是可公开验证的虚构演示，没有真实经营收益证明，也没有完整账号体系。您可以直接打开演示，或者先看九十秒操作视频。

## 现场验证清单

演示前在自己的浏览器试一次，并预留外部服务等待时间。不要把恢复码、访问令牌或后台凭证展示给面试官。

1. **打开公开页**：无痕窗口访问演示地址，确认十个模板出现、实时服务可用，无需登录 Vercel。
2. **填一份虚构资料**：选咖啡店模板，改成每天 60 杯、复购 20%、一周预算 200 元，目标观察七天复购变化；确认全部为虚构。
3. **提交一次分析**：点击分析，等待完成。核对报告是否有摘要、证据/推断/缺失信息、七个不同日期的动作；出现外部服务错误时保留提示，使用原资料恢复或重试。
4. **保存一天记录**：将第 1 天设为已完成，填写虚构指标和结论，保存。不要为了展示批量保存七天。
5. **刷新核对**：确认最近报告、第 1 天状态、指标和结论恢复一致；展开资料快照，核对原输入。正常成功流程使用三次共享 POST 请求：分析、保存、恢复。

四类接口合计每 IP 每 10 分钟最多五次。如果当前网络已用过额度，等待下一窗口或改为播放视频；不要用反复点击、换 IP 或关闭保护来演示。恢复旧报告时，要明确说“这是已有结果”，不称为本次新生成。

## 八个追问，答到有证据的范围

| 面试官可能问 | 回答要点 | 可以指到哪里 |
| --- | --- | --- |
| 代码是你写的吗？ | 使用 Codex / AI 辅助，不称所有代码都是手写。分别讲自己确认的需求、亲自操作的平台配置和目前能解释的机制。 | [个人参与说明](case-study.md#个人参与与-ai-辅助) |
| 为什么不用直接聊天？ | 受限输入、结构校验、资料快照和执行记录把一次回答变成可核对的流程；商业结论仍需真实验证。 | [输入和输出模型](../app/schemas.py) |
| 怎么保证重试不重复？ | 已完成记录按请求 ID 返回已有结果；输入变更被拒绝。进程内同编号加锁，飞书创建使用固定 client_token 防重复入库。跨实例模型调用没有持久任务锁，不能承诺“恰好一次”计费。 | [PipelineService.submit](../app/services/pipeline.py) |
| 模型输出不合格怎么办？ | Python 校验完整结构、七个不同日期，以及证据/推断/缺失信息；校验或上游调用失败后返回稳定错误码，保留可恢复状态。 | [AnalysisOutput](../app/schemas.py)、[DifyClient](../app/services/dify.py) |
| 没有登录，谁能修改记录？ | 记录读写依靠专属访问令牌，UUID 本身不授权。恢复码持有人能读写；没有账号找回、逐条撤销和完整修改历史。 | [TrackingService.authorize](../app/services/tracking.py) |
| 有真实效果吗？ | 十份虚构资料验证了接口、存储和恢复能力；没有十家真实客户，也没有营收提升证据。 | [真实集成验收](live-acceptance.md) |
| 保存日志会增加 AI 费用吗？ | 不调用模型，只更新飞书对应日期字段；原分析不会因日志变化自动重新生成。外部模型调用及平台仍受额度与可用性影响。 | [TrackingService.save_execution](../app/services/tracking.py) |
| 商用前先补什么？ | 先补真实资料授权与隐私规则、账号归属与凭证管理，再补并发防重、持久任务和监控。按实际需求设计，当前均不称为已完成。 | [限制与失败处理](failure-cases.md) |

## 先用半小时读懂这四处

| 时间参考 | 读什么 | 读完要能自己说明什么 |
| --- | --- | --- |
| 0–8 分钟 | `app/schemas.py` 的 `ScenarioDraft`、`AnalysisOutput` | 为什么限制十个字段；为什么校验七天和三种观察 |
| 8–16 分钟 | `app/services/pipeline.py` 的 `submit` | 先查记录还是先调用模型；完成结果怎么恢复；冲突与超时如何处理 |
| 16–23 分钟 | `app/services/tracking.py` 的 `authorize`、`save_execution` | UUID 与授权的区别；为什么保存一天不会覆盖其他天或重新调用 AI |
| 23–30 分钟 | `static/tracking.js` 的 `refresh`、`saveDay` | 浏览器怎样恢复最近报告；为什么读取失败时锁住保存 |

如果这些还不能解释，先读代码并亲自操作，再使用保守职责表述。材料帮助组织已经理解的内容，不能替代个人参与和技术掌握。
